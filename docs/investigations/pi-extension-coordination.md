# Cross-extension coordination for Pi session context

## Finding

A versioned broker advertised through `pi.events` is the closest working pattern for a central `pi-session-context` writer with separately installed contributors. The provider owns files and publishes a broker with asynchronous `putSession`, `putRuntime`, and attachment methods. A client listens for availability, requests an announcement, and calls the broker directly. This avoids a write protocol built from correlation IDs and reply channels. A small client import can carry types and discovery logic, but must not own storage or expect a module-level singleton across extensions.

### Why the current settings approach loses registrations

`pi-extension-settings` listens to `pi-extension-settings:register` when its extension factory runs. Consumers emit the registration once during their own factory. The [README](https://github.com/juanibiapina/pi-extension-settings#for-users) explicitly requires the provider to appear first in Pi's package list: an early emission is lost. Its imported `getSetting` and `setSetting` helpers read/write settings files separately from the UI extension. That works for settings, but does not give the proposed session-context provider sole ownership of its sidecar and runtime records.

Pi's [loader](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/extensions/loader.ts) creates Jiti with `moduleCache: false` for each extension. [Package documentation](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md) also says installed packages have separate module roots. Importing one package's module-level `Map` from another extension is not a reliable shared registry.

### Working patterns found

1. **Request/available broker: Codex Conversion.** Its [preflight client](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-conversion/src/code-mode-preflight.ts) subscribes to a versioned `available` channel, emits a versioned `request`, and registers on the broker object received. The [broker](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-conversion/src/tools/code-mode/nested-tool-preflight.ts) listens for requests and announces itself both at startup and when asked. Registrations return an unsubscribe function; the broker invokes callbacks with `await`, propagating or isolating failures according to the operation. Its [completion client](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-conversion/src/code-mode-hooks.ts) uses the same discovery. This handles either extension load order. A session storage broker can expose async write methods that resolve after atomic persistence.
2. **Pull-based contributor snapshot: Codex Conversion.** Its [Code Mode tool registration](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-conversion/src/code-mode-extension-tools.ts) registers each tool provider as an event listener. The host emits a request when it needs a snapshot; listeners synchronously add their current provider functions. A separate refresh event signals changes. This avoids startup registration order for read-only discovery. It does not by itself provide acknowledgement of persisted writes.
3. **Request/reply RPC: pi-subagents.** [Cross-extension RPC](https://github.com/tintinweb/pi-subagents/blob/master/src/cross-extension-rpc.ts) listens on versioned request channels, performs asynchronous work, and emits results on per-request reply channels. A [Pi service-registry proposal](https://github.com/earendil-works/pi/issues/4207) cites this as proof that RPC can work, while describing its correlation-ID and timeout cost. The proposal was auto-closed during a Pi refactor, not accepted as a built-in service interface. One comment first suggested module-scoped accessors, then corrected that advice after noticing Pi's isolated Jiti caches; it suggested `globalThis`/`Symbol.for` instead. A broker object carried over `pi.events` avoids that process-global registry.
4. **Replay on session start: pi-provider.** Its [adapter extension contract](https://github.com/hyav/pi-provider/blob/main/docs/adapter-extensions.md) emits a versioned registration at factory time and repeats it synchronously on `session_start`. The host builds its registry after receiving replays. This avoids the load-order loss for registration metadata, but is insufficient as the acknowledgement path for an asynchronous storage write. Pi's [extension lifecycle](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md) starts long-lived resources at `session_start` and releases them at `session_shutdown`.

## Monorepo layout in Pi Codex Conversion

The [repository root manifest](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/package.json) is private and declares `workspaces: ["packages/*"]`. Each package has its own `package.json`, Pi manifest, README, checks, and npm version. The [core manifest](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-conversion/package.json) loads one extension entry and exports separate helper subpaths such as `./code-mode` and `./code-mode-hooks`. The [web-run add-on](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-web-run/package.json) loads its own entry point. Its [factory](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-codex-web-run/index.ts) registers a normal tool and optionally imports Code Mode integration at runtime, with explicit missing-package handling.

The optional [aggregate package](https://github.com/IgorWarzocha/howaboua-pi-stuff/blob/main/packages/pi-extensions/index.ts) lists extension packages as dependencies and invokes their factories in a fixed order; users can install it instead of choosing packages individually. A bundle controls order only when that bundle is installed. Separately installed packages still need the broker discovery pattern. Pi does not automatically enable an extension just because another package depends on it.

For our setup, use one repository with independent packages under `packages/`: `pi-session-context`, `pi-tmux`, `pi-socket`, `pi-plans`, `pi-github`, and `pi-skills`. Export the broker client as a separate subpath from `pi-session-context` (or a stateless client library package), and load the provider extension exactly once. The monorepo allows one pinned Git revision for all packages in Nix. Since Pi does not install dependencies for local-path packages, any consumer importing the client at runtime must have it linked under `node_modules` in its deployment assembly, as the existing `pi-powerbar` derivation does for its dependencies. An optional aggregate package can follow after standalone packages work; do not depend on it for correctness.

## Consequences for `pi-session-context`

- Register the provider's discovery listeners in its extension factory. Announce the broker after registration and answer later discovery requests. Clients subscribe before requesting, compare a versioned protocol tag, and replace/dispose an old broker on reload. On `session_start`, reconnect or verify the handle before using it.
- Publish an object with a small interface: `register(namespace, payloadVersion)`, `putSession(ctx, namespace, data)`, `putRuntime(ctx, namespace, data)`, `getSession(ctx)`, `getRuntime(ctx)`, and attachment operations if plans keep editable files. Async methods resolve only after persistence succeeds. Avoid passing mutable internal maps to contributors.
- A client import should contain types and broker discovery only. It must not import the provider extension factory or read/write the provider's files. Use a scoped package export such as `@.../pi-session-context/client`, with the provider installed as an enabled Pi extension separately. Pi does not auto-load extension entry points from another package's npm dependency.
- Registration before provider discovery can wait for an announcement; if unavailable when the caller needs storage, fail with an explicit provider-missing error. Do not drop operations or claim an `emit()` has completed a write: Pi's [event bus](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/event-bus.ts) does not await async event handlers.
- Test client-first and provider-first loads, provider absent, incompatible protocol version, duplicate provider, `/reload`, session change, two concurrent namespace writes, and I/O failure. Test against Pi's actual event bus and loader as well as isolated fake clients.

## Open point

A feature that requires centrally managed persistence needs the provider extension enabled. A feature package can install without other feature packages, but cannot persist session contributions with the provider absent. Distribution needs an explicit installation rule because an npm dependency supplies imported code, not an enabled Pi extension.
